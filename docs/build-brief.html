Barista Build Brief

Everything in your ai-barista-adk folder, explained so you can defend it out loud — what each file does, what happens to one message, and the answers to the questions you will actually be asked.

Start with this

If someone asks “what did you build?”, this is the whole answer. Say it slowly; it takes about fifty seconds.

The spoken version

“It’s a barista agent for a coffee shop. You chat with it and it recommends a drink — but it can only recommend drinks we actually serve, because it isn’t answering from memory. Every time you ask it something, the agent calls a Python function that searches our menu file, and it only sees the drinks that function hands back. That’s the RAG part: retrieve first, then generate from what was retrieved.”

“The other half is allergies. If you tell it you’re lactose intolerant, that gets passed into the search and dairy drinks are removed before the model ever sees them — so the model isn’t being trusted to remember what has milk in it. It’s a filter in code, not a judgement call by the AI.”

“It’s built on Google’s Agent Development Kit with Gemini, the UI is Streamlit, and it deploys to Cloud Run straight from source — no Dockerfile.”

Two sentences to have ready if they only want the headline: the model never invents a drink, because it only sees what the search function returns. And allergen filtering happens in Python before the model is involved, not in the prompt.

The parts

Six files, and the one thing to know about each

menu.json
Eight drinks. Each has a name, price, description, tags, and allergens. This is the entire knowledge base. There is no database. If a drink isn’t in here, the barista cannot offer it.
menu_tool.py
The search_menu() function — scores drinks against what the customer asked for, and removes anything with a blocked allergen. This is the “retrieval” in RAG. Plain Python, no AI inside it. It imports nothing from Google, which is why its test runs with no API key.
agent.py
Creates the ADK LlmAgent: which Gemini model, the instruction telling it how to behave, and the list of tools it may call. Roughly forty lines, and half of them are the instruction. This file is the “agent” the grading asks about.
app.py
The Streamlit chat window: message history, the sidebar menu, and the code that sends your message to the agent and waits for the reply. Streamlit re-runs this entire file top to bottom on every keystroke. That’s why history lives in st.session_state and not in a normal variable.
test_menu.py
Nine checks on retrieval and allergen safety. Run with .\venv\Scripts\python.exe test_menu.py. Offline and free — no key, no network, no cost. Run it before you present; it’s your proof the allergen filter doesn’t leak.
requirements.txt
Four pinned dependencies: google-adk 2.2.0, google-genai 2.19.0, streamlit 1.56.0, python-dotenv 1.2.3. Cloud Run reads this file to build the container. Pinned versions mean the deployed app matches what you tested.

The mechanism

One message, end to end

This is the diagram to draw on a whiteboard if you’re asked how it works. The teal path is the part that makes it RAG.

The same trip in words, using the real values from your test run:

  1. You type “I’m lactose intolerant. I’d like something sweet and cold.” Streamlit appends it to st.session_state.messages and hands it to the runner.
  2. The runner loads the conversation for your session id and sends Gemini the whole history plus a machine-readable description of the one tool it’s allowed to call. ADK builds that description automatically from search_menu’s type hints and docstring — you never wrote a JSON schema.
  3. Gemini decides to call the tool. This is the step people mean by “agent”: the model chose to search rather than answer, and picked the arguments itself. 
    { "query": "sweet and cold",
  "exclude_allergens": ["lactose"] }
  4. Your Python runs — no AI involved. "lactose" is mapped to the menu’s label "dairy", every dairy drink is removed, and the rest are scored against the words “sweet” and “cold”: a tag match is worth 3, a name match 2, a description match 1. 
    matches:  Decaf Soy Caramel Macchiato, Cold Brew,
          Espresso, Oat Milk Flat White
excluded: ["dairy"]   // 5 drinks removed before the model saw them
  5. Gemini writes the answer using only those four drinks, taking the price from the retrieved data rather than from memory: “I highly recommend our Decaf Soy Caramel Macchiato for $5.35…”
  6. Streamlit displays it. The customer reads a reply built from those four drinks and nothing else — the other five were never in the model’s context to mention.

The claim to defend

Is this “real” RAG?

Yes, and you should be ready for the question, because your retrieval is a keyword scan rather than a vector database. Here’s the honest position.

RAG means retrieve, then generate: fetch relevant data at question time and make the model answer from that data instead of from its training. Your app does exactly that. Retrieval happening via keyword scoring rather than embeddings is an implementation choice inside the retrieval step — it doesn’t change whether the pattern is RAG.

Why the choice is defensible here: the corpus is eight items. An embedding model cannot out-retrieve exact matching on eight items, but it would add an embedding API call to every question, a vector index to build, and a database to run. The grounding — the property being graded — is identical either way.

Where embeddings genuinely win, and you should say so unprompted: a question with no shared words with the menu. “Something to wake me up” ought to find Cold Brew, and your keyword scan won’t make that connection. Say it before they find it — knowing your system’s limit reads as competence, and the fix is one function body, because search_menu() is the only thing that touches retrieval.

The framework

What ADK is actually doing for you

Worth being precise about, since “I used the Agent Development Kit” invites “to do what?”

ADK pieceWhat it does
LlmAgentHolds the model name, the instruction, and the tool list. It runs the loop: ask the model, notice it wants a tool, run the tool, hand the result back, repeat until the model answers.
Tools from functionsYou passed tools=[search_menu]. ADK read the type hints and docstring and generated the function schema Gemini needs. That is why the docstring in menu_tool.py is written for the model to read, not for you.
Runner + sessionStores the conversation and replays it each turn. This is why “What’s in it?” works — the model still has the earlier turns, including your allergy.
AppA named wrapper around the root agent. The unit you hand to a runner.

Sessions are held in memory. Refresh the browser and the conversation is gone. Fine for a demo, and worth naming as a known limit before anyone asks.

Your own decisions

Three calls you should be able to own

These are the places the build departs from the codelab. If you’re asked “what was hard?” or “what did you decide?”, these are the answers — each one was a real bug avoided.

run_async() instead of run_debug()

The codelab calls runner.run_debug(). Its own docstring in the installed SDK says it is for debugging and experimentation only, and that production should use run_async(). This is going to a public URL, so it uses run_async() — which also gives access to the individual events, so each tool call and its result can be read off the stream while debugging rather than staying hidden inside a helper.

The session has to be created explicitly

Runner has auto_create_session = False by default, so calling run_async() with a brand-new session id raises SessionNotFoundError — the app would have crashed on the very first message. _ensure_session() in app.py looks for the session and creates it if missing. run_debug() hid this by doing it for you.

Unsafe drinks are named, not hidden

Originally the allergen filter removed unsafe drinks so completely that the agent couldn’t tell “we don’t sell that” from “that would hurt you”. Asked about hazelnut, it said we don’t have any — which is false; there is a Hazelnut Mocha, it just contains dairy. The tool now also returns unsafe_matches, and the instruction requires naming them honestly. It now says: “We do serve a Hazelnut Mocha, but it contains dairy, so it isn’t safe with your lactose intolerance.”

Why it mattered: someone told “we don’t have that” may go looking for it elsewhere. This is the one failure in the app with consequences off the screen.

Deployment

One codebase, two environments

No code branches on environment — the Google SDK reads environment variables and picks its own backend. That is the answer to “how does auth work in production?”

Locally there is no gcloud CLI, so application default credentials aren’t available — hence the key. In the cloud a service account is free, so nothing secret needs storing. The switch is GOOGLE_GENAI_USE_ENTERPRISE=TRUE (the older name GOOGLE_GENAI_USE_VERTEXAI still works).

The deploy is source-based: Cloud Buildpacks read requirements.txt and build the container. No Dockerfile — a likely question, and that is the answer.

On the day

Demo script

Four prompts, in this order. Each demonstrates a different graded property, so say which as you type it.

  1. “I want something strong and iced” → Cold Brew. Say: “that came from the menu file, not the model’s memory” — then point at the sidebar: same drink, same price, read straight out of menu.json.
  2. “I’m lactose intolerant but want something sweet” → the Decaf Soy Caramel Macchiato, and nothing with dairy. Say: “five drinks were removed in Python before the model saw the list.”
  3. “Do you have anything with hazelnut?” → admits the Hazelnut Mocha exists but is unsafe for you. Say: “it stays honest instead of pretending we don’t stock it.”
  4. “What’s in it?” → answers about the drink from turn two without asking which. Say: “that’s the ADK session — the conversation is replayed on every turn.”

Have .\venv\Scripts\python.exe test_menu.py already run in a terminal tab. Nine passing checks on allergen safety is a strong thing to be able to point at.

Contingency

If it breaks while you’re presenting

The single most likely failure is not a bug in your code. It is the free-tier quota, and the app shows a plain message about the coffee machine being backed up rather than a stack trace.

Quota is per model. During testing gemini-3.6-flash and gemini-3.7-flash both throttled while gemini-3.5-flash — the default — kept answering on the same key in the same minute. Two things worth knowing:

  • 429 or 503 means quota, not breakage. The API words it as “high demand”, which sounds like Google’s problem; it is usually your key’s.
  • Switching model needs no code change: $env:BARISTA_MODEL="gemini-3.7-flash" then streamlit run app.py. On Cloud Run, add ,BARISTA_MODEL=… to --set-env-vars.

Deployed on Cloud Run it is less likely — Vertex AI bills against project quota, not the AI Studio free tier.

Preparation

Questions you’ll be asked

The last three are the uncomfortable ones. They are the ones worth rehearsing.

How do you know it isn’t making up prices?

Three reasons, in increasing strength. The instruction forbids recommending anything the tool didn’t return. The model only ever sees the drinks the tool returned, so there is nothing else to draw on. And every price in a reply can be checked against the menu in the sidebar, which is rendered from the same menu.json the retrieval reads — if the two disagree, the model invented something.

How does it remember my allergy across the conversation?

The ADK session stores the conversation and replays it to the model each turn, so the allergy is still in context. The instruction then requires passing it in exclude_allergens on every later call. You can see it working in the trace: by turn three the query has changed to “hazelnut” but exclude_allergens is still ["lactose"].

Why no vector database or Firestore, like the codelab shows?

Eight menu items. Exact matching retrieves at least as well as embeddings at that size, so a vector index would add an embedding call per question, an index to maintain, and a database to run, with no improvement to the grounding. The trigger to add it would be the menu growing past roughly fifty items, or wanting semantic matches like “something to wake me up”.

What happens when the menu changes?

Edit menu.json and redeploy. Nothing to re-index, no embeddings to regenerate — a genuine advantage of this design, not just a shortcut. The sidebar in the app is rendered from the same file, so the UI cannot drift out of sync with what the agent knows.

Why Streamlit rather than a proper web framework?

It gives a complete chat interface — history, message bubbles, input box — in about a hundred and thirty lines, and it is what the lab specifies. The cost is that Streamlit re-runs the whole script on every interaction, which is why the runner and the event loop are cached with st.cache_resource and history lives in st.session_state.

Isn’t this just keyword search with a chatbot on top?

Don’t get defensive; agree with the description, then draw the line. Yes — retrieval is keyword search. That is the R in RAG, and the pattern is defined by grounding the generation in retrieved data, not by the retrieval algorithm. What makes it an agent rather than a search box is that the model decides when to search and what to search for: it turned “I’m lactose intolerant, something sweet and cold” into a query plus a structured allergen filter, and carried that filter forward for the rest of the conversation without being told to.

What’s the weakest part of your build?

Answer this one honestly and specifically — it is the question that separates people who built something from people who watched it get built. Two real weaknesses:

  • Retrieval can’t match paraphrase. A question sharing no words with the menu (“something to wake me up”) won’t find Cold Brew. Fix: embeddings inside search_menu(), which is the only place that would change.
  • Sessions are in memory. Refreshing the page loses the conversation, and if Cloud Run scales to more than one instance, two requests could land on different instances with different memory. Fix: a persistent session service such as Firestore.
Would you trust this with someone’s real allergy?

The careful answer, and the true one. The filtering itself is deterministic Python with a test asserting it never leaks — not a judgement by the model — and customer wording is mapped onto menu labels, so “lactose”, “milk” and “cream” all block dairy. That is the right architecture: the safety-critical step is code, not a prompt.

What it still depends on is the model passing the allergy through correctly, and menu.json being accurate. For a real shop I’d want the allergen data owned by whoever owns the recipes, and a note telling customers to confirm with staff. I wouldn’t claim a language model in the loop is medically safe.

Vocabulary

Words to be able to define

In your own words, briefly. Hesitating on one of these is what makes a build look borrowed.

Agent
A model that can decide to take actions — here, deciding to search the menu — rather than only producing text.
Tool / function calling
Giving the model a description of a function it may call. The model doesn’t run your code; it replies “call this, with these arguments”, and the framework runs it and returns the result.
RAG
Retrieval-Augmented Generation. Fetch relevant data at question time and have the model answer from that, instead of from what it memorised in training.
Grounding
The property that an answer traces back to real supplied data. Here the reply is composed only from the rows search_menu() returned, so it traces back to menu.json rather than to training data.
Instruction
The standing brief in agent.py that shapes every reply — tone, when to call the tool, and the rules about allergens.
Session
The stored conversation. It is why the agent can resolve “what’s in it?” without asking what “it” is.
Buildpack
How Cloud Run builds a container from your source. It detects Python, reads requirements.txt, and produces an image — so you never wrote a Dockerfile.
Service account
An identity for software rather than a person. On Cloud Run the app authenticates to Gemini as itself, which is why no API key is deployed.
