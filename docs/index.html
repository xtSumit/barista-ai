AI Barista Agent

A conversational coffee recommender that cannot invent a drink. Every recommendation is retrieved from a menu dataset before the model speaks, and allergen filtering happens in Python — not in the prompt.

429 lines of Python 4 dependencies 6 offline tests 0 Dockerfiles 0 secrets in the repo

The problem it solves

Point a language model at a coffee shop and it will happily recommend a drink you don’t sell, at a price you never set, containing an ingredient the customer is allergic to. All three failures come from the same cause: the model is answering from memory rather than from your data.

This project closes that gap with two rules, both enforced in code rather than requested in a prompt:

  • The model only sees what was retrieved. Every question triggers a search over the menu, and the model’s context contains those results and nothing else. There is no drink available to invent.
  • Allergen filtering happens before the model is involved. Unsafe drinks are removed by a Python function, so safety never depends on the model correctly remembering which drinks contain milk.

The result is a chat interface that behaves like a well-briefed member of staff: it recommends from the actual menu, quotes real prices, remembers your allergy for the rest of the conversation, and is honest when the thing you want isn’t safe for you.

Architecture

How one message works

The teal path is the retrieval step — the part that makes this Retrieval-Augmented Generation rather than a chatbot with a system prompt.

Traced with real values, for the question “I’m lactose intolerant, I’d like something sweet and cold”:

  1. The runner assembles the turn — the stored conversation plus a machine-readable schema for the single tool the agent may call. The schema is generated from the Python function’s type hints and docstring; no JSON schema is written by hand.
  2. The model chooses to retrieve, and writes its own arguments. This is the step that makes it an agent rather than a search box: free-text intent becomes a structured query plus a safety filter. 
    { "query": "sweet and cold",
  "exclude_allergens": ["lactose"] }
  3. Python runs, with no model involvement. "lactose" is normalised to the menu’s "dairy" label, every dairy drink is dropped, and survivors are scored against the query — a tag match worth 3, a name match 2, a description match 1. 
    matches:  Decaf Soy Caramel Macchiato, Cold Brew,
          Espresso, Oat Milk Flat White
excluded: ["dairy"]   // 5 of 8 drinks removed pre-model
  4. The model composes the answer from those four drinks, taking the price from retrieved data rather than memory — and the UI records which drinks the answer was grounded in, shown inline as Grounded in 4 menu items.

Codebase

Six files

menu.json
The knowledge base — eight drinks with tags, allergens, price and caffeine content. No database; edit and redeploy.
menu_tool.py
Retrieval and allergen filtering. Imports nothing from Google, so it is testable with no credentials and no network. The R in RAG.
agent.py
The ADK LlmAgent — model, instruction, tool list. Half of it is the instruction.
app.py
Streamlit chat UI, conversation history, and the async plumbing that survives Streamlit’s re-run-everything execution model.
test_menu.py
Six assertions covering retrieval relevance and allergen safety. Plain assert, no framework. Runs offline and free.
requirements.txt
Four pinned dependencies. Read directly by Cloud Buildpacks at deploy time.

Engineering

Decisions worth explaining

Each of these is a place where the obvious approach was wrong, and the reasoning is more interesting than the code.

Keyword retrieval, not a vector database

On an eight-item corpus, embeddings cannot out-retrieve exact matching — but they would add an embedding call per question, an index to build, and a database to operate. The grounding property is identical, so the complexity buys nothing. The honest limit: a query sharing no vocabulary with the menu (“something to wake me up”) won’t match. Retrieval is isolated in one function, so upgrading it touches one file.

Allergen filtering is deterministic, and speaks the customer’s language

Safety-critical logic doesn’t belong in a prompt. Filtering is plain Python with a test asserting it never leaks, and an alias map so real phrasing works — “lactose”, “milk” and “cream” all block dairy, “coeliac” blocks gluten. That last one matters more than it looks: the oat milk drink contains gluten, which is exactly the trap a hand-written prompt would miss.

Filtered drinks are reported, not erased

The first working version had a subtle honesty bug. Asked “anything with hazelnut?” by a lactose-intolerant customer, it answered we don’t have any — false, because the Hazelnut Mocha exists; the filter had hidden it so completely the model couldn’t distinguish “not on the menu” from “not safe for you”.

The tool now returns unsafe matches alongside safe ones, and the instruction requires naming them honestly while never offering them. A customer told “we don’t have that” might go looking for it elsewhere — the one failure mode here with consequences off the screen.

A single long-lived event loop, not asyncio.run() per message

Streamlit re-runs the entire script on every interaction, on a possibly different thread. asyncio.run() closes its loop on return, while the cached API client keeps connections bound to the loop that made them — so the first message works and the second fails with “Event loop is closed”. The fix is one loop on a daemon thread, fed with run_coroutine_threadsafe. Verified by driving three messages from three different threads.

Production API over the convenience helper

The framework offers a one-line helper for running an agent. Reading its source showed a docstring stating it is for debugging only and that production should use the streaming API. Taking the longer path also exposed the individual tool-call events — which is what makes the “grounded in N items” disclosure possible. It also surfaced a default that would have crashed the first message: sessions are not auto-created, so the app creates its own.

One codebase, two credential models

Locally the app authenticates with an API key from an ignored .env. Deployed, it authenticates as its own service account and no key exists anywhere in the image or config. No code branches on environment — the SDK selects its backend from environment variables, so the deployed artifact is byte-identical to what was tested.

The model name is configuration

Normally a constant that never changes shouldn’t be configurable. This one earned it: over the build, three model identifiers failed in three different ways — one retired for new keys, two rate-limited — and quota turned out to be per-model rather than per-project. Four model changes, zero code edits.

Honest limits

What it doesn’t do

  • Retrieval is lexical. Paraphrase with no shared vocabulary won’t match. The upgrade is embeddings inside the one retrieval function.
  • Sessions are in memory. A page refresh loses the conversation, and horizontal scaling would split conversations across instances. The upgrade is a persistent session store.
  • Allergen data is only as good as the file. The architecture puts the safety-critical step in tested code rather than in a prompt, which is the right shape — but a language model in the loop is not a medical guarantee, and real deployment would want the allergen data owned by whoever owns the recipes.

Each limit has a named fix and a trigger for applying it. None were hit by this scope.

Deployment is source-based: the platform’s buildpacks read requirements.txt and produce a container, so there is no Dockerfile to maintain and no image registry step to script.

Questions

Design questions, answered

Is keyword search really RAG?

RAG describes the pattern — retrieve relevant data at question time, generate the answer from it — not the retrieval algorithm. Swapping keyword scoring for embeddings changes recall on paraphrased queries; it doesn’t change whether the generation is grounded. At eight items, exact matching has the better cost-to-benefit ratio, and the boundary is one function when that stops being true.

How is the model prevented from inventing drinks and prices?

Structurally rather than by instruction. The model’s context contains only the retrieved drinks, so there is no other menu item available to mention. The instruction reinforces it, and the UI displays what was retrieved for each answer, which makes any drift visible rather than silent.

Why not put the allergen rules in the prompt?

Because prompts are probabilistic and allergies aren’t. A filter in code can be asserted in a test; a sentence in a prompt can only be hoped for. It also scales better — adding a drink means adding a line to a data file, not re-editing prose that enumerates ingredients.

What makes this an “agent” rather than a chatbot?

The model decides when to retrieve and what to retrieve. Given “I’m lactose intolerant and want something sweet and cold”, it produced a search query and a structured allergen filter, then carried that filter through the rest of the conversation unprompted. Nothing in the code parses the customer’s sentence.

How does deployment handle secrets?

It doesn’t need to. Locally there is an API key in a gitignored file; in the cloud the container authenticates as its own service-account identity, so no credential is stored in the image, the config, or the repository. The same code handles both because the SDK reads its backend from the environment.
